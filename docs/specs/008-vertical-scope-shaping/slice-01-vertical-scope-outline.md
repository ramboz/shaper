## Slice 008-01 — vertical-scope-outline

**Goal:** `shape-release` captures a release's new work as an ordered list of
thin, end-to-end **vertical scopes** (thinnest demoable path first), written
into the release plan — so work reaches jig already delivery-ordered instead of
as a single "main user-facing path" lump.

**DoR:**
- ✅ ADR-0005 records the vertical-scope decision (Option C).
- ✅ `templates/release-plan.md` and `skills/shape-release/SKILL.md` are the
  edit surfaces (both read; current shape confirmed in ADR-0005 A1).

**Acceptance Criteria:**

1. **The release-plan template carries a vertical-scope list.** The
   `## Solution Outline` section of `templates/release-plan.md` gains a
   "Vertical Scopes (delivery order)" subsection: an ordered list where each
   entry names a thin end-to-end scope and its demoable outcome, with the first
   entry explicitly the thinnest walking-skeleton path. The existing "Main
   user-facing path" / "Important non-goals" fields are preserved.
2. **`shape-release` elicits and writes the scopes.** `skills/shape-release/SKILL.md`
   "Inputs to gather" lists the vertical-scope decomposition as a field to
   elicit, and the "Writing or refining a plan" steps write it into the plan;
   omitted scopes leave a `TBD` marker (consistent with the skill's existing
   TBD rule), never a fabricated ordering.
3. **The order is asserted to be vertical, not horizontal.** The skill instructs
   that each scope must deliver end-to-end value (an anti-horizontal-phasing
   check, mirroring jig's SPIDR rule) — a scope that is "just the data model" or
   "just the parser" is re-split. This instruction is present in the skill body.
4. **The deterministic helper round-trips the field.** If
   `skills/shape-release/scripts/shape_release.py` writes plan fields, it accepts
   and emits the vertical-scope list (or leaves `TBD`); a create/refine run
   preserves any user-authored scope wording (append-not-overwrite, per the
   skill's existing refine rule).
